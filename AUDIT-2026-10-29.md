# LumaFlow review — 29 October 2026

## Outcome and scope

LumaFlow has a useful foundation: native Qt UI, separate capture and transport code,
independent device tasks, atomic settings replacement, and an existing regression
suite. Preserve that architecture and the accepted dark interface. Improvements can
be delivered incrementally without replacing the application.

This review used the supplied handoff as background, then inspected the current
source, tests, launch/build scripts, and documentation. Instructions in the handoff
were not treated as a request to implement its entire development roadmap.
Application source and existing tests were not changed. No physical devices were
connected or controlled by this review, and the user's running app was left alone.

## Validation performed

- Windows, local virtual environment, Python 3.14.7, Qt offscreen.
- Installed pytest into the existing project virtual environment.
- Existing suite: **64 passed in 6.09 seconds**.
- Command: `.venv\Scripts\python.exe -X faulthandler -m pytest tests -q -o faulthandler_timeout=30`

- The initial sandboxed run stalled while Python created its event-loop socket pair.

- Additional isolated probes used temporary settings and fake devices. Results below

- No physical BLE, WASAPI capture, startup registration, packaged EXE, real WLED, or
  real OpenRGB acceptance was performed. Existing tests do exercise a local WLED HTTP
  server and mocked device operations.

## Confirmed findings to fix first

### 1. Continuous controls can queue stale settings

Sources: `app.py:188`, `app.py:221`, `model.py:57`, `engine.py:104`, `engine.py:189`.

Every slider value change synchronously saves the settings file on the GUI thread
and submits a complete settings snapshot. The engine processes one command per
iteration, then sleeps for 15 ms. Latest-frame device output does not prevent a
backlog of settings commands.

Reproduction: programmatically sweeping the brightness slider from 0 to 100 generated
101 saves and 101 queued settings commands. Draining that queue took **2.05 seconds**
in this run, with no hardware involved. Actual pointer gestures may generate fewer
events, but the queue has no replacement mechanism for obsolete values.

Recommended change: apply controls to live state immediately, replace pending
continuous-control updates with their newest values, and debounce disk persistence
by approximately 200–300 ms. Flush pending saves on exit. Keep explicit device,
disconnect, off, and quit actions separate so they cannot be discarded or wait behind
obsolete slider values. Measure response after the change.

Acceptance: a rapid slider gesture reaches its final requested value promptly,
pending obsolete values do not grow without bound, and restart retains the final value.

### 2. Stereo channel cancellation can cause false music blackout

Source: `signals.py:73`.

The music pipeline averages channels before measuring RMS and computing the FFT.
Equal-and-opposite channels cancel, even when each channel contains a strong signal.

Reproduction using a 100 Hz sine wave at amplitude 0.2:

| Input | Requested intensity | Spectrum peak |
| --- | ---: | ---: |
| Mono | 1.0 | 1.0 |
| Same-phase stereo | 1.0 | 1.0 |
| Opposite-phase stereo | 0.0 | 0.0 |

Recommended change: compute channel energy before combining loudness, and combine
per-channel spectral magnitudes or power rather than cancelling waveforms. Preserve
the silence gate, sensitivity, and exact-zero behavior. Add stereo regression cases.

Acceptance: opposite-phase stereo stays reactive; true silence still produces zero.

### 3. Loaded settings are not fully type-validated

Source: `model.py:23`.

Numeric ranges and some enumerations are checked, but boolean settings and device
fields are not fully validated. Calling `str(value)` does not validate or replace
the stored value.

Reproduction: a settings file containing `resume: "false"`, `enabled: "false"`,
`verified: "false"`, null device name/address, and an unknown profile loaded without
a warning. The string `"false"` is truthy in Python. This can change the meaning of
connection, verification, and capture preferences in a malformed or hand-edited file.
Ordinary saves from the current UI use real booleans; this finding concerns load and
future import boundaries.

Recommended change: validate types, enums, IDs, and adapter-specific device fields;
preserve explicit opt-outs; recover individual invalid fields when possible; keep
recoverable backups and show a clear warning. Version migrations explicitly.

Acceptance: malformed preferences cannot silently enable resume or device output;
valid saved devices and existing migration behavior survive recovery.

### 4. Failed-device retry instructions do not match the available action

Sources: `engine.py:161`, `engine.py:172`, `app.py:246`, `app.py:269`.

With reconnection disabled, a failed connection leaves a completed task in the task
map and reports "Offline · click Connect to retry". The device remains enabled, so
the UI button is actually "Disconnect". Resubmitting unchanged enabled settings does
not retry. Disconnect followed by Connect is the current workaround.

Recommended change: provide an explicit Retry action for an offline device, restart
that device's completed task, and make the label match its current state. Keep manual
disconnect persistent and distinct from temporary failure.

Acceptance: one Retry click makes one new attempt without turning on automatic retries
or changing other devices.

## Reliability and usability improvements

These are recommendations or validation gaps, not newly proven hardware failures.

1. **Dedicated Lights off action.** Keep Pause as "hold last color". Off should
   request zero output on connected devices, report failures, and preserve mode
   brightness preferences. Define what happens when an offline device reconnects.
2. **Source recovery.** Capture errors currently pause the app. Add an obvious source
   error with Retry; enumerate actual monitors and audio devices; handle default audio
   changes, monitor removal, and Windows sleep/wake. Respect an intentional Pause.
3. **Useful diagnostics.** Preserve bounded local crash/error logs across restarts,
   include tracebacks and last successful-send age, and offer address/name redaction
   on export. Keep requested output distinct from physical LED feedback.
4. **Display and input usability.** Test small usable desktop areas and 125–200% display
   scaling. The current minimum window is 950 by 760 logical pixels. Prefer named
   monitor choices over an arbitrary 1–16 spinner. Verify keyboard focus visibility,
   control labels, and contrast in the actual Windows app.
5. **Repeatable releases.** Select and test a release Python version, lock tested
   dependency/build versions, and align local and CI build commands. The handoff
   suggests Python 3.13; this local test used 3.14.7. Test a packaged EXE on a clean
   Windows account/machine without Python, including the OpenRGB helper.
6. **Measured transport behavior.** Retain safe BLE pacing until measured on the
   controller. Two packets for a changing native brightness and color limit practical
   update speed. Do not promise that a faster preview means faster physical lighting.

For persistent bounded logs, Python supplies rotating file handlers:
https://docs.python.org/3/library/logging.handlers.html#rotatingfilehandler

## Proposed customization

Introduce an **Edit layout** mode while retaining a useful default workspace.
Changes to the layout should not interrupt the lighting engine.

Suggested built-in panels:

- Live lighting preview.
- Current mode and its relevant controls.
- Brightness and quick actions, including Off.
- Device connection status.
- Favorite colors and saved scenes.
- Music spectrum, relevant when Music is active.
- Optional diagnostics.

Let users add available panels, hide them, reorder them, and choose supported sizes.
Use clear drop positions; include Move up/Move down or equivalent keyboard/menu
alternatives. Add Undo, Lock layout, and Reset layout. Prevent a broken layout from
making core controls inaccessible.

Keep three preferences separate:

| Preference | Example | What it stores |
| --- | --- | --- |
| Workspace | Minimal, Movie desk, Music studio | Panel arrangement and visibility |
| Lighting preset | Cinema, Gaming, Relax | Mode and its lighting parameters |
| Appearance | Mint accent, compact spacing | Theme, density, text and motion preferences |

Named local profiles can let people sharing a Windows account keep different
preferences. Windows users already have separate LocalAppData settings. Accounts
and a cloud service are not required for this initial customization.

Implement stable panel IDs and a versioned, validated layout schema. Store layout
separately from device verification, manual-disconnect state, and live lighting
settings. Start by extracting reusable panels from the existing UI and preserve the
accepted visual design. This can be a sequence of small changes.

Qt already supports movable dock widgets and saving/restoring their arrangement;
that is one implementation option. A constrained card grid may better preserve the
current Studio design. Shared layout imports should use validated structured panel
data rather than arbitrary serialized Qt window state.
Reference: https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QMainWindow.html

Per-device screen regions are a separate lighting feature. The current NBBUFF pair
shares one controller output; layout customization cannot make the two bars
independently addressable. Add zone controls only for adapters and hardware with
established support.

## Suggested delivery order

1. **Change safety:** initialize local Git history, exclude the virtual environment,
   caches, builds, and private diagnostics; record the passing baseline. Keep each
   behavioral change small and independently reviewable.
2. **Stability release:** fix the four confirmed findings with focused regressions;
   add Off and clear error/retry feedback. Retain existing mode behavior and migration.
3. **Windows acceptance:** verify physical RGB/brightness, black-to-bright recovery,
   quiet/loud/silent audio, disconnect/reconnect, sleep/wake, tray/startup, and packaged
   EXE behavior. Run a long session while monitoring responsiveness and memory.
4. **Personalization:** add favorite colors and named lighting presets first, then
   modular panels, saved workspaces, and appearance controls. Verify that changing
   layouts does not change lighting output or reconnect devices.

The workspace was not a Git repository at review time. Git setup is a recommendation;
it was not performed during this review. No application fixes or customization
features described above have been implemented yet.
